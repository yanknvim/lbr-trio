# ハンドオフテンプレート

`build` → `review`、`review` → `leader` の報告と、`leader` → 人間の要約で使う。
報告の前にこのファイルを読み、必要な書式をコピーして埋める。

## 1. 受領 ACK

報告を受け取った下流は、着手前に 1 行で返す。

```text
ACK: 起点 abc1234、範囲 abc1234..def5678 を確認します
```

ACK が届いた時点で、上流は次の作業を開始してよい。
ACK がない場合は、送信側から再度短く問い合わせる。

## 2. 作業報告ヘッダ（build / review）

報告の冒頭 6 行。該当なしは「なし」と明記する。

| 欄 | 内容 |
|---|---|
| 起点 | 前回レビュー済みのコミット、または作業開始時の HEAD |
| 範囲 | `起点..HEAD`。区切りが複数ある場合は列挙する |
| 変更ファイル | パスと役割（要件 / 計測 / 実装 / 文書） |
| 指摘→対応 | 前回指摘の採否。初回は「なし」 |
| 検証条件 | 実行したコマンドと条件名 |
| 未確認事項 | 実機待ち・外部依存など。チェックリストがあれば ID を併記 |

詳細な経緯はヘッダの後に置く。
検証ログは本文に貼らず、ファイルパスで参照する。

## 3. 根拠タグ

数値・外部仕様・実機挙動の断定には、根拠の強さを示すタグを付ける。
それ以外の記述には付けなくてよい。

- `[source: path:line]` ソースで確認した
- `[test: コマンド]` 実行して確認した
- `[host]` ホスト上のプレビューで確認した。正しさの根拠にはしない
- `[unverified]` 未確認。完了条件から分離する

タグのない数値・外部仕様の断定は、レビューで要修正とする。

## 4. 指摘の採否表（build）

| 指摘 | 採否 | 理由 | 対応コミット |
|---|---|---|---|
| 例: 設定の重複 | 採用 | 2 回実行で重複を確認 | abc1234 |

保留には「何が分かれば再検討するか」を 1 行添える。

## 5. 指摘の書き方（review）

要修正・提案のそれぞれに、次を付ける。

- 修正案
- 受け入れ条件（観測可能な形。件数・再実行結果・終了コードなど）
- 確認コマンド

主観的な条件は、数値・件数・再実行結果に置き換える。

## 6. leader から人間への要約

3 項目だけ。レビュー範囲や変更ファイルは書かない。

| 欄 | 内容 |
|---|---|
| 判断材料 | 決めるべきことと選択肢 |
| 未確認 | 人間の確認が必要な項目 |
| 次の action | 人間が取る操作、または次に動くロール |

## 7. 委任文に貼るブロック

`leader` は最初の委任で次をそのまま貼る。

```text
報告は docs/handoff-template.md の書式に従うこと。
先頭6項目: 起点 / 範囲 / 変更ファイル / 指摘→対応 / 検証条件 / 未確認事項
数値・外部仕様・実機挙動の断定には根拠タグを付けること。
完了後は review へ herdr で報告し、起点..HEAD を明記すること。
```
