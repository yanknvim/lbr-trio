## 0. 適用範囲と選別基準

本稿は、特定のボード・表示デバイス・ビルド環境・パッケージ管理に依存しないワークフロー原則だけを扱う。判定基準は「別の技術スタックやプロジェクトに、そのまま持ち込めるか」であり、固有の API 名・設定値・障害現象は、その裏にある一般原則に読み替えて記述する。固有の解決策は `docs/lessons-learned.md` 側に残し、本稿には一般原則だけを収録する。

## 1. 受け渡し・報告

### 1.1 ハンドオフテンプレート（2026-10-28 に3項目へ簡素化。以下は当時の記録）

- **改善**: 作業完了報告の冒頭を固定し、「起点 / 範囲 / 変更ファイル / 指摘→対応 / 検証条件 / 未確認 ID」の 6 項目を必須にする。
- **今回の実例**: 各ラウンドで「前回 HEAD / 追加レビュー起点 / 追加レビュー範囲 / 累積範囲」を先頭に置いたことで、レビューは差分 1 本に絞れた（例: `4d143a3..1ea1b43`）。報告本文は 5 本で各 2〜7KB あり、要点が後ろに埋もれる場面もあった。
- **次回適用方法**: 報告テンプレートの先頭 6 行を必須欄にし、該当なしは「なし」と明記する。詳細な経緯は後半に置き、検証ログはパス参照にする。
- **期待効果**: 受け手が「どこからどこまでを見るか」を解釈せずに済み、再レビューの立ち上がりが速くなる。報告も短くなる。

### 1.2 根拠タグ

- **改善**: 事実の記述に `[source: file:line]` `[test: コマンド]` `[host]` `[unverified]` のタグを付け、根拠の強さを明示する。タグのない断定はレビューで止める。
- **今回の実例**: 知見文書のうち、ソースで確認できない断定がレビューで複数修正された（`70c6416`）。報告と実装の説明が具体的だったため、ソースとの突き合わせ自体は速かった。
- **次回適用方法**: 報告テンプレートにタグの凡例を入れ、`[unverified]` が残る項目は完了条件から分離する。指示側にも `file:line` を求める（4.3）。
- **期待効果**: 「確認済み」と「推測」の混同が減り、レビューの指摘が根拠の補強に集中する。

### 1.3 レビューの 1 行 ACK（2026-10-28 に廃止。以下は当時の記録）

- **改善**: レビュー担当は受領時に「起点コミット + 見る範囲」を 1 行で返す。
- **今回の実例**: 実装担当が報告を送った後も、人間経由で同じ内容が流れ、どちらが正式な経路か毎回判断が必要だった（workflow 報告の 2.6）。送信側は「送った」と「読まれた」を区別できなかった。
- **次回適用方法**: 非同期チャネルで受領 ACK を必須にする。ACK は「起点 `abc1234`、範囲 `abc1234..def5678` を確認します」の 1 行でよい。
- **ACK の返信**: ACK は到達確認の終端であり、返信しない（1.8）。
- **期待効果**: 二重送信や見落としが減り、次の作業を開始してよいタイミングが明確になる。

### 1.4 ロール間の受け渡し経路の固定

- **改善**: 上流から下流への受け渡しは非同期チャネルを正式経路とし、人間には要約だけを返す。同じ内容を複数経路で流さない。
- **今回の実例**: 実装からレビューへの報告が、非同期メッセージと人間のメッセージの両方で流れる場面があった。人間は承認と実機確認に集中する、という分担が曖昧になった。
- **次回適用方法**: ロールごとの受け渡し経路を 1 つに決め、人間への返答は「判断材料の要約 + 次の action」に限定する。正式経路の内容は 1.1 のテンプレートで送る。
- **期待効果**: 経路の重複がなくなり、人間の介在が必要な判断に時間を使える。

### 1.5 セッション初回にロール規則を自己確認する

- **改善**: 各ロールはセッション初回に、自分のロール規則から「誰に・何経路で・何を送るか」を 3 点で確認してから着手する。
- **今回の実例**: レビュー担当が初回レビューの指摘を非同期チャネルで実装担当に送らず、報告書とユーザーへのチャットだけで終えた。初回は当該操作を試していないため、権限の有無は未確認である。ロール規則の「指摘は実装担当へ非同期で報告」を確認しなかったことが原因だった。2 回目以降はユーザーの指示がトリガーになって送信した。技術ではなく規則の認識漏れである。
- **次回適用方法**: 着手前チェックとして「報告先 / 経路 / 送る内容」を 3 行で書き、最初の作業ログに残す。送信後は 1.3 の ACK で到達を確認する。
- **期待効果**: 権限やツールの問題に見える抜けを、規則の確認漏れとして早期に防げる。人間の指示を待たずに受け渡しが完結する。

### 1.6 承認メッセージに報告先と経路を明示する

- **改善**: 承認や委任のメッセージに「完了後は X へ Y 経路で報告」を 1 行入れる。ロール規則に暗黙に依存しない。
- **今回の実例**: 承認時に報告先・経路を省略すると、規則を知っていれば自明でも実行時のトリガーにはならない。初回レビューでは指摘が非同期チャネルに流れなかった（1.5）。承認メッセージに報告先・経路が含まれていたかは記録に残っていないため原因とは断定せず、再発防止として承認時の 1 行を必須にする。
- **次回適用方法**: 承認テンプレートに「完了条件 / 報告先 / 報告経路 / 次の担当」を必須欄として設ける。自明でも省略しない。
- **期待効果**: 受け渡しの抜けが減り、承認した側も完了後の流れを把握できる。

### 1.7 人間の指示をトリガーにしない

- **改善**: 受け渡しや報告はロール規則をトリガーにし、人間の指示や中継を開始条件にしない。
- **今回の実例**: 初回レビューの指摘は、人間の指示が入るまで実装担当へ送られなかった。人間中継が挟まったことで「送った / 読まれた」が不確実になった。受領 ACK は当時の運用に組み込まれていなかった。
- **次回適用方法**: 作業完了時に、ロール規則で決めた次の担当へ自動的に送る。人間には要約を返し、判断が必要な点だけを依頼する。送信ログと ACK を残す。
- **期待効果**: 人間の在席や指示待ちに依存せず、受け渡しが止まらない。経路の不確実性も下がる。

### 1.8 ACK へは返信しない（2026-10-28 に ACK ごと廃止。以下は当時の記録）

- **改善**: ACK は到達確認の終端として扱い、返信しない。応答は次の着手そのもので表す。ACK に返信するターン（例: 「ACK を受領しました」の報告のみのターン）は徒労とする。
- **往復実測**: 2026-10-28 の lbr-demo 3 セッション（`ses_e806b5eb` / `ses_e80671dc` / `ses_e806b96e`）の記録を seq 順に照合すると、ACK への返信ターンは 5 件あり、5/5 がツール呼び出しゼロだった。内訳は「ACK を受領しました」3 件（build）と「完了です」2 件（review）[source: ~/.local/share/opencode/opencode.db ses_e806b5eb seq165→166, seq404→405, seq502→503; ses_e80671dc seq129→130, seq164→165]。委任時の集計は 4 件・4/4 で、生ログでは review 宛の 2 件目を加えて 5 件になる。返信しない運用との対照比較はしていない [unverified]。
- **ACK を残す範囲**: review の受領 ACK（起点 + 範囲）と leader の最終 ACK（完了判断）は必須。前者は、初回レビューの指摘が build 宛に送られず人間が中継した事故（m5paper-dashboard の改善文書 当時版 §1.5/1.6）の再発防止 [source: m5paper-dashboard 5c9f657:docs/improvement.md §1.5, §1.6]。後者は、完了判断の宛先と範囲を明示するため。herdr は非同期で、送信直後の `idle` は相手の着手前の状態しか表さないため、送信側は ACK なしに到達を判断できない [source: AGENTS.md:9]。
- **ACK 以外の到達検知がない理由**: 現行の通信経路で「届いて読まれた」ことを観測できるのは ACK だけ。同期的に返るエラー（送信失敗・agent not found）は「送れなかった」ことを示すが、到達や閲読は示さない [unverified]。したがって廃止するのは ACK そのものではなく、ACK への返信だけ。
- **次回適用方法**: 下流は ACK を受けたら返信を書かず、次の作業を開始する。返す内容がない場合はターンを終了する。上流は ACK の返信を待たない。
- **期待効果**: ACK 1 件ごとに発生していた着手ゼロの往復がなくなる。実測 5 ターン分の待機宣言が消える見込み（削減率は未計測 [unverified]）。

## 2. 検証

### 2.1 反復する検証のスクリプト化

- **改善**: 毎回同じ手順を組み直す検証は 1 コマンドに固定する。条件別の実行、中間成果物の無効化、結果の表形式出力までを含める。
- **今回の実例**: 同じ 3 条件の検証を毎回手で再構成し、ビルドログ 9 本・検証ディレクトリ 19 個が残った。中間成果物の無効化不備で数値が混ざり、報告値の再確認が必要になった（lessons §1.2）。
- **次回適用方法**: `tools/verify.sh` 的なスクリプトに「中間成果物の削除 → 条件別実行 → 失敗条件の明示 → 結果表の出力」を固定する。実装担当とレビュー担当が同じスクリプトを使う。
- **期待効果**: 1 ラウンド 3〜5 分程度の再構成がなくなる見込み（未実測）。条件の抜けや集計ミスも減る。

### 2.2 数値報告に条件名を必ず付ける

- **改善**: サイズ・件数・時間などの数値には、「どの条件で取得したか」を必ず添える。条件が違う数値を同じ表で比較しない。
- **今回の実例**: 同じ構成でも条件によって数値が変わり、報告値の再現確認に時間がかかった。条件を添えたことで、どの数値が実利用に近いかを後から判別できた（lessons §1.2、§1.6）。
- **次回適用方法**: 報告の数値表に「条件名 / 実行コマンド / 取得時刻」の列を設ける。条件が異なる行は分けて書き、合算しない。
- **期待効果**: 数値の誤読や再検証が減り、報告の比較可能性が上がる。

### 2.3 外部リソースは中身を確認する

- **改善**: 外部のインデックス・API・配布物は、HTTP 200 だけで成功と判断しない。Content-Type、先頭バイト、パース可否まで確認する。
- **今回の実例**: 外部インデックスが HTTP 200 で HTML を返し、期待した形式として使えなかった（lessons §1.1）。ステータスコードだけでは検知できなかった。
- **次回適用方法**: 取得直後に「Content-Type の確認 → 先頭バイトの確認 → パース」を自動化し、失敗時は明示的に停止する。URL は設定ファイル内の 1 箇所に集約する。
- **期待効果**: 上流の配布形式の変化を早期に検知でき、後工程での原因調査が減る。

### 2.4 ホストプレビューは「形の方向性」に限る（`[host]` タグは 2026-10-28 に `[unverified]` へ統合）

- **改善**: 実機や本番環境の代わりに作るプレビューは、見た目の方向性確認に限定する。正しさの根拠にはしない。プリミティブの意味を確認する場合は、実装と同じコードを移植する。
- **今回の実例**: 独自実装のプレビューが実装と同じ解釈誤りを再現し、レビューがソース突き合わせで見つけるまで 1 往復増えた（lessons §1.4）。一方、文字幅・列幅・間隔の確認には有効だった。
- **次回適用方法**: プレビューには `[host]` タグを付け、根拠欄には載せない。プリミティブ検証用のプレビューは、実装と同じアルゴリズムを移植したものに限る。
- **期待効果**: プレビューの長所を残しつつ、「見えるから正しい」という誤判断を防げる。

## 3. 履歴・文書

### 3.1 コミット分離と起点..HEAD の明記

- **改善**: 要件・診断・実装・文書を作業単位でコミット分離し、報告に「起点..HEAD」と各コミットの役割を書く。
- **今回の実例**: 要件 `04d80af`、診断 `b876b02`、実装 `6fe86c6`、文書 `a1cde3b` を分けたことで、再レビューは `git diff <起点>..<HEAD>` の 1 本で済んだ。診断は仮説が外れても revert 不要だった。
- **次回適用方法**: 1 コミット 1 役割を原則にし、報告の先頭に範囲と各コミットの役割を書く。要件変更と実装を同じコミットに混ぜない。
- **期待効果**: レビュー範囲が明確になり、手戻り時の巻き戻しコストが下がる。

### 3.2 要求文書の同期ルール

- **改善**: 意味が変わる変更は同一コミットで要求文書に反映する。数値の微調整はコード定数に集約し、要求文書には「最終値はコード定数」と 1 行だけ置く。
- **今回の実例**: 表示サイズ 21pt→18pt、座標 +3〜+6px などの変更が報告にだけ残り、コードの定数と要求文書が食い違った。一方で、一部の意味変更は `04d80af` で要求文書に反映済みだった。
- **次回適用方法**: 変更を「意味が変わる変更」と「数値微調整」に分類する。前者は要求文書に 1 行追記、後者はコード定数と報告の表に集約する。
- **期待効果**: 後から参加した人が、要求と実装のどちらが正かを追わずに済む。

### 3.3 実機・外部環境依存項目の ID 付きチェックリスト

- **改善**: 実機や外部環境でしか確認できない項目は、ID 付きのチェックリストに一元化する。チェックリストは実装の前段階で作り、診断ログの設計にも紐づける。
- **今回の実例**: 濃度・字形・向き・周期・接続などの確認待ちが、報告・要求文書・README に分散した。周期の診断では、確認待ち項目が先に分かっていたから必要なログを設計できた（lessons §1.5）。
- **次回適用方法**: 解釈・設計の段階で `docs/hardware-checklist.md` 的な 1 ファイルを作り、各項目に ID を振る。報告では「チェックリストの○番」と参照し、診断ログも同じ ID に紐づける。
- **期待効果**: 確認漏れが減り、実機待ちの項目が報告から消えない。診断の設計も後追いにならない。

## 4. 意思決定

### 4.1 事前承認フローの定型化

- **改善**: 着手前に「環境調査で判明した事実の表」と「明示承認が必要な 3〜5 点」を分けて提示し、承認後に実装する。
- **今回の実例**: 初回の解釈リストは 15KB、明示承認は 5 点。仕様レベルの手戻りは 0 件で、初回レビューの要修正は実装の不具合 1 件に収まった（lessons §1.7、workflow 報告）。
- **次回適用方法**: 事実表（調査結果）と承認表（判断してほしい点）を別々に作り、承認表は 3〜5 点に絞る。承認後に解釈を変える場合は 3.2 の同期ルールに従う。
- **期待効果**: 実装中の仕様判断が減り、手戻りとレビュー論点のずれが抑えられる。

### 4.2 不具合は修正より先に計測を分離する

- **改善**: 原因仮説が立ったら、修正コミットの前に計測用のコミットを切る。計測は挙動を変えず、ログと観測手順だけを追加する。
- **今回の実例**: 診断コミット `b876b02` は +79 行、挙動変更なし。実測で仮説が否定され、修正コードを書かずにクローズできた（lessons §1.5）。
- **次回適用方法**: 「計測コミット → 実測 → 修正するか判断」の順を固定する。計測コミットには、観測手順と判定条件を README かチェックリストに書く。
- **期待効果**: 仮説が外れたときの revert・再レビュー・再検証が不要になり、履歴も汚れない。

### 4.3 指示に含める事実は file:line 付きで、方針と分離する

- **改善**: 指示やレビューで事実を伝えるときは `file:line` を添え、「事実」と「採用方針」を別欄にする。事実が不正確だった場合は、方針と切り離して訂正する。
- **今回の実例**: ライブラリ仕様に関する事実が不正確なまま、方針だけが先に固定された。実装後に事実を補足し、「事実」と「採用方針」を分けて記録した（lessons §1.4）。
- **次回適用方法**: 指示テンプレートに「事実（根拠付き）」「採用方針」「未確認」の欄を設ける。実装担当は指示とソースが食い違ったら、黙って従わず事実を返す。
- **期待効果**: 誤った前提の固定を防ぎ、方針変更と事実訂正を混ぜずに議論できる。

### 4.4 具体的な指摘と受け入れ条件

- **改善**: 指摘は「修正案」と「受け入れ条件（何を満たせば完了か）」をセットで書く。完了条件は観測可能な形にする。
- **今回の実例**: 設定更新の修正依頼で、「既存設定を保持したまま 2 回実行して重複しないこと」という受け入れ条件を付け、修正が 1 回で完了した（lessons §5.1 の 6、build 報告 5.1 の 6）。
- **次回適用方法**: 指摘テンプレートに「修正案 / 受け入れ条件 / 確認コマンド」を必須欄として設ける。主観的な条件は、数値・件数・再実行結果に置き換える。
- **期待効果**: 修正の往復が 1 回で済み、再レビューの合否判断も明確になる。

### 4.5 指摘の採否表（採用 / 保留 + 理由）

- **改善**: レビュー指摘への対応を「採用 / 保留 + 理由」の表で返す。保留には再検討条件を添える。
- **今回の実例**: 初回レビューの提案 3 件を採用 2・保留 1 と理由付きで返し、次のラウンドで同じ論点が蒸し返されなかった（lessons §5.1 の 6、build 報告 5.1 の 6）。
- **次回適用方法**: 報告テンプレートに「指摘 → 採否 → 理由 → 対応コミット」の表を入れる。保留は「何が分かれば再検討するか」を 1 行で書く。
- **期待効果**: 判断の履歴が残り、同じ論点の再議論を防げる。

### 4.6 委任条件は着手可能性ベースにする

- **改善**: 委任は「指示の完全性」ではなく「着手可能性」で行う。未確定値は既定値で解釈リストに仮置きし、人間の意思決定は委任の待ち時間に並行させる。確定値は解釈リスト承認時に反映する。
- **今回の実例**: 2026-10-27 18:54:35 の指示（leader セッション、msg_17cc87ad2001KEtfiMmn7ryu6f）では、ユーザーが「@m5paper-dashboard-plan.md をもとにダッシュボードを作りたい」と指示した。これに対し、@grill-me による質問→回答→要求文書の作成→委任を直列化したため、実装担当が待機した。人間の決定を実装前に直列に置いた点が、非同期並行の原則（どのロールも完了待ちのターンを持たない）と衝突した。
- **次回適用方法**: 着手前に「着手可能か / 何が未確定か / 既定値で進められるか」を判定する。未確定値は解釈リストに仮置きし、人間の決定を待たずに実装を開始する。確定値の反映は 3.2 の同期ルールに従う。
- **期待効果**: 人間の判断待ちと実装が並行し、最初の着手までの待ち時間が短くなる。委任する側の直列化も防げる。

## 5. インフラ

### 5.1 エージェント再起動後のロール設定復旧と起動後確認

- **改善**: エージェントの既定の動作モードは、起動経路（環境変数・起動方法）に依存する。再起動時はロール設定を明示して起動し、起動後にロール名と動作モードを確認する。
- **今回の実例**: 2026-10-28 06:53 JST 頃、build ペインの再起動でロール設定が失われ、意図と違うモード（plan モード）で起動した。復旧手順と出典は `docs/lessons-learned.md` §5.4、再起動時の注意は `tools/assemble.sh` のコメントに残した。
- **次回適用方法**: ロール設定をペインやセッションの作成時に渡す仕組みを用意し、再起動時は設定付きで作り直す。起動後にロール一覧とモードを確認し、想定と違えば作業を始めない。
- **期待効果**: ロールの取り違えによる誤操作や、権限・モードの誤認を早期に防げる。

### 5.2 権限設定と一時領域

- **改善**: 検証・レビュー用の権限を必要最小限にし、書き込みは命名規則付きの一時領域に限定する。拒否される操作の代替手段を事前に決め、後片付けを検証スクリプトに含める。
- **今回の実例**: レビュー側は書き込み・破壊的操作が拒否され、検証を一時領域に限定できた。一方、後片付けの削除コマンドも拒否され、一時物が残った（lessons §1.7）。
- **次回適用方法**: 一時領域の命名規則（例: `/tmp/<project>-<purpose>-<timestamp>`）を決め、検証スクリプトの開始時・終了時に作成・削除する。権限で拒否される操作には、読み取り専用の代替や新しい一時領域を使う手順を用意する。
- **期待効果**: 事故リスクを下げつつ、検証後の環境が汚れない。

## 6. すぐ導入できる 3 点

1. **検証スクリプト（`tools/verify.sh` 的）**
   - 中間成果物の削除、条件別の実行、結果表の出力を 1 コマンドにまとめる。まずは現在の 3 条件（既定・実利用相当・部分構成）を固定する。
   - 完了条件: 実装担当とレビュー担当が同じコマンドを実行し、同じ表を報告に貼れること。

2. **報告ヘッダ**
   - 共通の3項目ヘッダ（範囲 / 検証 / 未確認事項）と根拠タグの凡例を `AGENTS.md` に固定する。
   - 完了条件: 報告の冒頭 10 行以内で、レビュー範囲と未確認事項が分かること。

3. **実機・外部環境チェックリスト**
   - 解釈・設計の段階で `docs/hardware-checklist.md` 的な 1 ファイルを作り、項目に ID を振る。診断ログと報告は ID で参照する。
   - 完了条件: 実装完了時点で、未確認項目がチェックリストの ID だけで列挙できること。
